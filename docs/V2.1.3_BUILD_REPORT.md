## 3. 根因与证据

### 3.1 第一层：会话开始时工作区授权写入失败

本次第一条命令即报 Harness 授权失败，而非项目错误：

```text
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(D:\cyberpath)
```

说明会话启动时无法为工作区写入授权项。使用 Windows 沙箱 ACL 诊断脚本检查后确认：`D:\cyberpath` 缺少有效的 `WRITE_OWNER`（所有者仍是当前用户，但受限令牌无法使用所有者隐式权限）。脚本为该目录追加当前用户的完全控制项并**验证通过**（`writeDac: true → writeOwner: true`），随后根目录恢复可写。

这只解决了根目录，**并没有解决 EPERM**——这正是继续排查的起点。

### 3.2 第二层（真正原因）：Low 完整性令牌无法写入 Medium 对象

| 证据                         | 观察                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| 沙箱命令令牌                 | `Mandatory Label\Low Mandatory Level`（`S-1-16-4096`）；Administrators 为 deny-only；仅保留 `SeChangeNotifyPrivilege` |
| 根目录标签                   | `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`                                        |
| 新建目录标签                 | 自动继承为 Low，读写删全部正常                                                            |
| `src`/`docs`/`.git`/`.next-v2` | **没有完整性标签**（默认为 Medium）                                                       |
| DACL                         | Authenticated Users 有 Modify，所有者为当前用户；除 Harness 自身的 `Everyone DeleteChild` 拒绝项外无拒绝项 |

对照实验（同一沙箱命令、同一进程内用 Node 执行）：

| 目标                                  | 结果                          |
| ------------------------------------- | ----------------------------- |
| 项目根目录新文件                      | 成功                          |
| 新建子目录内新文件                    | 成功                          |
| `src/probe.txt`                       | `EPERM -4048`                 |
| `docs/probe.txt`                      | `EPERM -4048`                 |
| `.next-v2/probe.txt`                  | `EPERM -4048`                 |
| `.git/probe.txt`                      | `EPERM -4048`                 |

关键点：错误码是 `EPERM` 且 errno 与构建错误完全一致（`-4048`）。Windows 的强制完整性控制（MIC）在 Low 令牌尝试“向上写” Medium 对象时返回访问拒绝，而 DACL 本身是允许的——这与观察完全吻合。新建目录之所以正常，是因为它在创建时继承了根目录的 Low 标签；既有对象仍是 Medium。

**反证实验：** 对 10 个项目子目录执行 `icacls ... /reset /T`，把 ACL 恢复为纯继承状态（`src` 因此重新获得 Harness 的可继承写授权项 `(I)(OI)(CI)(W,D,DC)`）。执行后 `src` 的 DACL 已包含写权限，但写入**仍然 EPERM**——这排除了 DACL 问题，把原因锁定在完整性标签。

### 3.3 为什么无法自行彻底修复

设置完整性标签属于 SACL 操作，需要 `SeSecurityPrivilege`：

```text
> icacls src /setintegritylevel "(OI)(CI)L"
src: Access is denied.   (exit 5)
```

当前令牌为 Medium、未提权，且本次任务禁止擅自使用管理员权限，因此**没有**修改完整性标签，也没有关闭 Defender/防火墙或改动项目外文件。
