## 1. 项目在学习中的位置

CyberPath 把学习分成四层，四层缺一不可：

```
知识（Lesson / Quiz）
  → 练习（Lab，聚焦单一机制）
    → 项目（Project，跨模块交付）
      → 证据（Evidence，可被第三方复核）
```

- **课程**回答「是什么、为什么」。
- **实验**回答「这个机制怎么动」。
- **项目**回答「你能不能在约束下做出来」。
- **证据**回答「别人能不能相信这是你做的」。

项目不是课程的装饰，而是能力判定的主要依据。完成课程但无项目，只能证明「学过」；有项目但无证据，只能证明「展示过」。

## 4. 重点项目规格

### 4.1 P-01 家庭网络安全体检（P0）

- **场景**：为自己或家人的设备做一次安全检查，不接触任何他人系统。
- **任务**：列出设备与账号；检查更新、备份、密码与 MFA；检查路由器管理口令与 Wi-Fi 加密；给出 5 条可执行改进。
- **交付物**：检查表（含截图或文字记录）、风险清单（可能性×影响）、改进计划。
- **验收**：每项检查有证据；风险排序有理由；建议不包含「关闭安全软件」。
- **安全**：不修改他人设备；不扫描公网；截图打码个人信息。

### 4.2 P-03 命令行文件整理器（P1）

- **场景**：把一个混乱目录按扩展名/日期归档，并生成报告。
- **任务**：实现 dry-run 与 apply 两种模式；处理重名与权限错误；写测试；用 Git 分阶段提交。
- **交付物**：可运行脚本、README（用法与限制）、至少 5 个测试、提交历史。
- **验收**：dry-run 不修改文件；错误可读；重复执行安全；README 能让陌生人运行。
- **反作弊**：现场修改一条规则并重新运行。

### 4.3 P-07 简易 HTTP API + 数据库（P2）

- **场景**：为学习档案提供 CRUD API。
- **任务**：设计资源与状态码；实现校验、分页与错误体；建表与迁移；写集成测试。
- **交付物**：源码、schema、迁移脚本、API 文档、测试报告。
- **验收**：非法输入被拒绝；分页边界正确；迁移可回滚；无 SQL 拼接。
- **反作弊**：现场增加一个字段并完成迁移。

### 4.4 P-09 Linux 服务器加固基线（P3）

- **场景**：把一台默认配置的主机加固到可对外提供服务的基线。
- **任务**：账号与 SSH、防火墙、服务最小化、日志、补丁、备份；写检查脚本与回滚步骤。
- **交付物**：基线脚本、加固前后对比（配置与扫描）、回滚手册、残余风险清单。
- **验收**：每条加固项可验证；回滚实测成功；不锁死自己（保留可用访问路径）。
- **安全**：仅在自有虚拟机或授权主机操作。

### 4.5 P-10 Web 应用安全评估（P3）

- **场景**：对自建应用做一次完整评估。
- **任务**：威胁建模；认证/授权/输入/输出测试；复现至少 3 类问题；修复并回归。
- **交付物**：威胁模型、测试记录、发现清单（含证据）、修复 PR、回归结果。
- **验收**：每个发现可复现；修复含测试；报告区分「已验证」与「疑似」。
- **安全**：仅测试自有应用；不测试第三方。

### 4.6 P-11 检测规则与 SIEM 告警（P3）

- **场景**：为一个小型环境建立检测能力。
- **任务**：采集日志；为 3 类行为写规则；构造测试事件；评估误报；写处置手册。
- **交付物**：规则文件、测试事件、告警样本、误报分析、运行手册。
- **验收**：规则能命中测试事件；误报有量化；规则有假设与盲区说明。

### 4.7 P-14 云上三层架构与 IaC（P3）

- **场景**：用代码部署一个 Web + 应用 + 数据库的三层架构。
- **任务**：VPC/子网/安全组；计算与负载均衡；数据库；IAM 最小权限；Terraform 模块化。
- **交付物**：IaC 代码、架构图、成本估算、部署与销毁记录。
- **验收**：`plan` 可审查；无公开存储；销毁可清理；无硬编码密钥。
- **成本控制**：使用免费额度或本地模拟；完成后必须销毁。

### 4.8 P-18 综合项目：安全加固的全栈服务（P4，Capstone I）

- **场景**：从零交付一个可被他人部署的全栈服务。
- **任务**：需求与范围；架构与 ADR；认证授权；输入输出安全；测试；容器化；部署手册；威胁模型。
- **交付物**：仓库、运行说明、ADR、威胁模型、测试报告、演示视频或现场演示。
- **验收**：
  - 陌生人按 README 可在 30 分钟内启动；
  - 所有受保护端点有服务端授权；
  - 关键路径有自动化测试；
  - 安全检查无高危未处理项；
  - 答辩能解释 3 个关键取舍。
- **红线**：硬编码密钥、无法复现、伪造测试结果。

### 4.9 P-19 多服务系统与事故复盘（P4，Capstone II）

- **场景**：把单体拆为 2–3 个服务，注入故障并完成响应。
- **任务**：定义服务契约；加队列/重试/幂等；部署与可观测性；做一次故障演练；写复盘。
- **交付物**：部署清单、仪表盘、演练脚本、时间线、复盘、改进项跟踪。
- **验收**：故障可被监控发现；定位到组件与版本；复盘改进项有验证；系统可回滚。
- **安全**：故障注入仅在隔离环境，明确影响范围与停止条件。

### 4.10 P-20 公开漏洞/安全公告复现（P5）

- **场景**：选择一个公开 CVE 或安全公告，在隔离环境复现并分析。
- **任务**：阅读公告与补丁；搭建隔离环境；复现；分析根因与缓解；写报告。
- **交付物**：环境说明、复现步骤、根因分析、缓解评估、参考来源。
- **验收**：来源可追溯；复现可重复；分析区分事实与推测；不提供可直接用于攻击他人系统的武器化内容。
- **伦理**：仅在隔离虚拟机；不扫描公网；遵守公告与法律。

## 5. Capstone 结构

### 5.1 时间盒（建议，不是承诺）

| 周 | P-18 | P-19 |
| --- | --- | --- |
| 1 | 需求、范围、威胁模型 | 服务边界与契约 |
| 2 | 核心功能与认证 | 部署与基础监控 |
| 3 | 测试与安全修复 | 队列/重试/幂等 |
| 4 | 部署手册与演示 | 故障演练与复盘 |
| 5 | 答辩与修订 | 改进项验证与答辩 |

### 5.2 答辩要求

- 15 分钟演示 + 15 分钟问答。
- 必须包含：架构图、关键取舍、失败案例、下一步。
- 评审至少 2 人（导师 + 同伴）；单人评审需录制并抽样复核。

### 5.3 不通过条件

- 无法现场运行或无法解释核心代码。
- 无法说明安全边界与失败模式。
- 证据缺失或与仓库历史不一致。

## 6. 评分 rubric

### 6.1 维度与权重

| 维度 | 权重 | 0 分 | 1 分 | 2 分 | 3 分 |
| --- | --- | --- | --- | --- | --- |
| 技术正确性 | 30% | 无法运行 | 能运行但主要功能缺失 | 功能完整、边界正确 | 正确且有取舍说明 |
| 安全与伦理 | 20% | 有红线行为 | 有明显安全缺陷 | 基本控制到位 | 威胁模型驱动、可验证 |
| 测试与验证 | 20% | 无测试 | 少量手工验证 | 关键路径自动化 | 含失败路径与回归 |
| 文档与可复现 | 15% | 无文档 | 有零散说明 | README 可复现 | 含限制、回滚、运维 |
| 表达与答辩 | 15% | 无法解释 | 能描述步骤 | 能解释取舍 | 能迁移到新问题 |

### 6.2 通过标准

- 加权得分 ≥ 2.0 / 3.0；
- 任一维度不得为 0；
- 无红线项；
- Capstone 额外要求答辩通过。

## 8. 作品集标准

### 8.1 每个项目必须有

1. **一句话问题**：解决什么问题，给谁用。
2. **运行方式**：依赖、命令、预期输出。
3. **证据**：测试结果、日志、截图（打码）、演示链接。
4. **取舍**：为什么这样设计，替代方案是什么。
5. **失败与限制**：已知问题、未覆盖场景。
6. **安全与伦理**：数据来源、授权范围、隔离方式。

### 8.2 禁止

- 把教程项目原样复制为「独立完成」。
- 用截图代替可运行代码。
- 隐去失败与限制，只展示成功路径。
- 在作品中包含真实密钥、个人信息或未授权数据。

## 10. 评审与反作弊

### 10.1 评审流程

1. 自评：按 rubric 打分并附证据索引。
2. 同伴评审：至少 1 人，使用同一 rubric。
3. 导师/抽样复核：随机抽取 20% 项目进行现场问答。
4. 争议处理：以可复现证据为准，不以口头描述为准。

### 10.2 反作弊手段

- **现场变体**：随机修改一个需求，要求当场实现或解释。
- **历史检查**：Git 历史是否连续、是否有大段复制痕迹。
- **交叉提问**：询问设计取舍、失败案例、边界条件。
- **环境复现**：评审者在干净环境按 README 运行。
- **证据一致性**：报告中的数字与日志、截图、测试输出一致。

### 10.3 学术诚信

允许使用文档、开源库与 AI 辅助，但必须：

- 声明使用了哪些工具与库；
- 能解释提交的每一行关键代码；
- 不把他人项目声称为自己完成；
- 不伪造运行结果。

## 11. 安全与伦理

1. **授权**：任何测试必须获得书面授权或在自有环境进行。
2. **隔离**：攻击性实验在隔离虚拟机/容器中进行，默认无公网出口。
3. **最小影响**：验证漏洞使用最小必要动作，不破坏数据、不横向移动。
4. **数据**：不使用真实个人信息；截图打码；报告匿名化。
5. **披露**：发现真实漏洞时，遵循负责任披露流程，不公开可直接利用的细节。
6. **法律**：遵守所在地区法律与平台条款；不确定时停止并求助。
